## 3. Private-key policy

- Never put private keys (`id_ed25519`, `*.pem`, `*.key`), passwords, recovery codes, WireGuard private keys, or unredacted configuration files in GitHub, issues, PR comments, screenshots or this repository.
- A public SSH key ending in a comment such as a device label may be stored in an access inventory if necessary, but prefer recording its SHA-256 fingerprint and device label. Public keys are not passwords, yet should still be handled deliberately.
- Keep private keys on the device that uses them. Use OS keychain/agent or the trusted SSH app's secure storage; encrypt device backups.
- Use a distinct key per device so a lost phone can be revoked without rotating every other device.
- Protect private-key files with restrictive permissions on Unix-like systems (typically `chmod 600` for the private key and `chmod 700` for `~/.ssh`).
- If a key or device is lost or exposed, remove only that key's matching public-key entry from `authorized_keys`, then verify all remaining access paths.
- Do not disable password authentication, alter SSH port, change firewall rules, or restart SSH until key login is confirmed from a second session and the provider recovery console is available.

## 4. Key creation — perform later, after the SSH safety gate

### Main PC (Windows PowerShell)

Inspect existing keys first; do not overwrite an existing key:

```powershell
Get-ChildItem $HOME\.ssh
```

If a suitable dedicated key does not exist, create one with OpenSSH:

```powershell
ssh-keygen -t ed25519 -a 64 -f "$HOME\.ssh\aura_interserver_ed25519" -C "aura-admin-main-pc"
```

Choose a strong passphrase. The command creates a private key and a `.pub` public key. Only the public key may be installed on the VPS. Never paste the private-key content into a chat or repository.

Display the public key to install later through the already verified admin access:

```powershell
Get-Content "$HOME\.ssh\aura_interserver_ed25519.pub"
```

Do not run key installation until current access is confirmed and the existing `authorized_keys` file has been backed up securely. Prefer appending the new public key rather than replacing the file.

### Linux / Ubuntu client

Inspect before creating:

```sh
ls -la ~/.ssh
```

Create a dedicated key only if needed:

```sh
ssh-keygen -t ed25519 -a 64 -f ~/.ssh/aura_interserver_ed25519 -C "aura-admin-linux-client"
```

Keep the private key local. Install only the matching `.pub` key on the VPS after the safety gate.

### iPhone and Android

- Use a reputable SSH client that supports Ed25519 and protected key storage.
- Generate an individual key inside that client if possible.
- Export/copy only the public key for installation. Do not move the PC's private key to a phone.
- Label each public key with a non-sensitive device name and record its SHA-256 fingerprint.
- Test login before relying on the phone as an emergency recovery route.
- VPN configuration is a separate future task; do not create or import WireGuard profiles as part of SSH key setup.

## 7. Safe validation sequence

1. Confirm the provider console/rescue route works.
2. Keep the current SSH session open.
3. From the PC, verify the intended public key and test a second independent SSH session.
4. Confirm `sudo -v` and `sudo id -u` (expected output: `0`).
5. Record the public-key fingerprint, not the private key.
6. Test each additional device separately and revoke a test key only after confirming the primary PC key still works.
7. Review SSH socket/service activation and actual firewall rules before changing either.
8. Only after SSH and recovery are verified, plan hardening or WireGuard. Never bundle SSH, firewall, routing and VPN changes into one unverified step.

### 9.1 Failure signature and diagnosis

If a deploy run fails in seconds at the `Execute Zero-Downtime Deploy` step (`appleboy/ssh-action`) with:

```
ssh: handshake failed: ssh: unable to authenticate,
attempted methods [none publickey], no supported methods remain
```

the cause is SSH key authentication, not the deploy script. Check in order:
1. Is the public key matching the secret still in `~/.ssh/authorized_keys` on the VPS (compare fingerprints)?
2. Is the secret intact and a full OpenSSH private key (with BEGIN/END lines and final newline)?
3. Are permissions intact (`~/.ssh` 0700, `authorized_keys` 0600, owner `aura-admin`)?

### 9.2 Rotation / rebuild procedure (requires operator approval — SSH access gate)

1. On the VPS, generate a fresh pair in a temp directory and note its fingerprint:
   ```sh
   install -d -m 700 /tmp/opencode/ci-key
   ssh-keygen -t ed25519 -f /tmp/opencode/ci-key/aura-ci-deploy -N '' \
     -C 'github-actions-deploy-digitaleflex/aura-storage'
   ssh-keygen -lf /tmp/opencode/ci-key/aura-ci-deploy.pub
   ```
2. Append ONLY the public key (never overwrite existing entries). Set the
   checkout path explicitly and bind the installer to `aura-admin`, so a root
   or rescue-console shell cannot target `/root/.ssh/authorized_keys`:
   ```sh
   REPO_ROOT=/home/aura-admin/aura-storage
   TARGET_USER=aura-admin \
     bash "$REPO_ROOT/scripts/install-admin-key.sh" \
     --apply /tmp/opencode/ci-key/aura-ci-deploy.pub
   ```
3. Verify permissions: `~aura-admin/.ssh` 0700,
   `~aura-admin/.ssh/authorized_keys` 0600, owner `aura-admin`.
4. Upload the private half straight from file to secret (it must never be displayed, pasted or committed):
   ```sh
   gh secret set SSH_PRIVATE_KEY --repo digitaleflex/aura-storage \
     < /tmp/opencode/ci-key/aura-ci-deploy
   ```
5. Destroy the private key on the VPS and remove the temp files:
   ```sh
   rm -f /tmp/opencode/ci-key/aura-ci-deploy
   ```
6. Re-run the failed workflow (`gh run rerun <run-id> --failed`) or trigger it manually; confirm SUCCESS.
7. Update the fingerprint inventory in §6, then remove the old public-key line from `authorized_keys` **only after** the new key is proven working.

**Rule:** at every instant, at least one working access path must exist (operator's own key or rescue console) before touching any `authorized_keys` entry.
